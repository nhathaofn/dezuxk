# TEST_INFRA.md — E2E Test Infrastructure & Tiered Coverage Specification

## 1. Overview & Architecture

This document defines the comprehensive, opaque-box End-to-End (E2E) test infrastructure for **dezuxk** derived strictly from user requirements in `ORIGINAL_REQUEST.md` (R1-R4) and the feature inventory in `PROJECT.md` (Features 1-11).

The E2E test suite adheres to the **Dual Track Testing** principles:
- **Strictly Opaque-Box**: Tests interact only via public HTTP APIs, exported configuration loaders, domain storage contracts, and CLI subprocess execution.
- **Hermetic & Deterministic**: All upstream services (e.g. Google Flow) are simulated locally using `httptest.Server`. No external internet connectivity is required.
- **Progressive Testability**: Tests validate both current baseline capabilities and upcoming milestone deliverables without depending on internal private symbols.
- **Isolated Execution**: Every test instantiates isolated temporary state (`t.TempDir()`, transient SQLite databases, dedicated HTTP listener ports) and guarantees teardown.

## 3. Tiered Coverage Mapping

### Tier 1: Feature Coverage (>=5 test cases per feature)

#### Feature 1: Dynamic Master Key Resolution (R3)
- `T1_F1_01_ExplicitCLIKey`: CLI flag `--master-key` resolves as the active master key.
- `T1_F1_02_ExplicitENVKey`: Environment variable `DEZUXK_SECURITY_MASTER_KEY` resolves when no flag is provided.
- `T1_F1_03_ConfigFileKey`: Key specified in JSON config is resolved when no flag/env exists.
- `T1_F1_04_KeyFileResolution`: Master key loaded from explicit file or `.master.key` in `DataDir`.
- `T1_F1_05_AutoGeneratedEntropy`: Auto-generated master key produces valid 256-bit entropy without hardcoded secret fallback.
- `T1_F1_06_CryptographicRoundtrip`: Master key correctly initializes cipher for transparent secret encryption/decryption.

#### Feature 2: Dynamic Config Layering (R3, R4)
- `T1_F2_01_DefaultConfig`: Baseline production-safe defaults for host, port, db_file, data_dir.
- `T1_F2_02_ConfigFilePrecedence`: JSON config overrides default values.
- `T1_F2_03_EnvVarPrecedence`: Environment variables override config file and defaults.
- `T1_F2_04_CLIFlagPrecedence`: Command-line flags override all lower configuration layers.
- `T1_F2_05_APIKeyConfiguration`: API key configured via flags/env/file enables Bearer auth protection.

#### Feature 3: Declarative Provider Manifest Schema (R1)
- `T1_F3_01_ManifestJSONParsing`: Manifest JSON unmarshals into structured provider definition.
- `T1_F3_02_DomainAllowlistEnforcement`: Allowed domains array restricts egress targets.
- `T1_F3_03_ProbeRulesSchema`: Identity extraction and discovery keywords schema validation.
- `T1_F3_04_SecurityRulesSchema`: Security flags (anti_bot, proxy requirement) schema parsing.
- `T1_F3_05_CustomProviderManifest`: External third-party provider manifest definition loaded identically to default provider.

#### Feature 4: Manifest Loader & Validator (R1)
- `T1_F4_01_FileManifestLoader`: Manifest loader reads from single file path.
- `T1_F4_02_DirectoryScanning`: Manifest loader discovers and scans directory for multiple `.json` manifests.
- `T1_F4_03_MissingMandatoryFields`: Validator rejects manifests missing required fields (`id`, `name`, `base_url`).
- `T1_F4_04_InvalidURLValidation`: Validator rejects manifests with invalid URLs or unsupported protocols.
- `T1_F4_05_EmbeddedFallback`: Fallback to embedded default manifest when external manifest directory is empty.

#### Feature 5: Dynamic Provider Registry (R1)
- `T1_F5_01_RegisterProvider`: In-memory registration of provider with lookup by ID.
- `T1_F5_02_ListActiveProviders`: Query active providers excluding inactive/disabled ones.
- `T1_F5_03_DefaultProviderResolution`: Registry identifies and resolves default provider.
- `T1_F5_04_ConcurrentRegistryAccess`: Thread-safe concurrent reads and writes to provider registry.
- `T1_F5_05_SQLiteSync`: Provider registration persists to and synchronizes with SQLite storage.

#### Feature 6: Elimination of Hardcoded Seeding in Entrypoint (R1)
- `T1_F6_01_BootstrapWithoutHardcoding`: Gateway boots with zero hardcoded provider literals in entrypoint.
- `T1_F6_02_DynamicManifestLoadingOnStartup`: Gateway loads provider manifests dynamically from configured path.
- `T1_F6_03_CustomManifestDirCLI`: `--manifests-dir` CLI flag directs gateway to external manifests directory.
- `T1_F6_04_ManifestDirEnvVar`: `DEZUXK_MANIFESTS_DIR` configures manifest discovery path.
- `T1_F6_05_SubprocessStartup`: Service binary executes, boots, and binds HTTP port cleanly.

#### Feature 7: Account Pool Manager & Scheduler (R4)
- `T1_F7_01_AccountLeasing`: Available ready account is successfully leased from the pool.
- `T1_F7_02_FairRotationLRU`: Accounts are leased in round-robin / LRU order using `last_checked_at`.
- `T1_F7_03_RateLimitTransition`: Account status transitions to `rate_limited` with `paused_until` duration.
- `T1_F7_04_SignOutTransition`: Account status transitions to `signed_out` on authentication failure.
- `T1_F7_05_PoolStatsAccounting`: Pool correctly tallies ready vs total accounts for health monitoring.

#### Feature 8: Upstream Credential Injection (R2)
- `T1_F8_01_CookieDecryption`: Encrypted cookies decrypted and assembled into `Cookie: name=value; ...` header.
- `T1_F8_02_TokenDecryption`: Encrypted auth tokens decrypted and injected into headers (`Authorization`, `x-goog-api-key`).
- `T1_F8_03_CookieDomainPartitioning`: Cookies partitioned according to target domain pattern.
- `T1_F8_04_MultipleAccountIsolation`: Separate accounts maintain completely distinct credentials and cookies.
- `T1_F8_05_SecureTokenStorage`: Cookies and tokens are encrypted at rest in SQLite `account_secrets`.

#### Feature 9: Reverse Proxy Dispatcher & Failover (R2)
- `T1_F9_01_HermeticUpstreamDispatch`: Gateway dispatches image generation to mock upstream HTTP endpoint.
- `T1_F9_02_HeaderPropagation`: Upstream receives properly formatted user-agent, cookies, and tokens.
- `T1_F9_03_RetryOnTransientError`: Upstream 5xx error triggers retry attempt.
- `T1_F9_04_FailoverOnRateLimit`: Upstream 429 triggers account cooldown and failover to next pool account.
- `T1_F9_05_FailoverOnUnauthorized`: Upstream 401/403 triggers account signout and failover to next pool account.

#### Feature 10: Elimination of Mock & Hardcoded Handler Logic (R2)
- `T1_F10_01_DynamicImageResponse`: Image generation returns response sourced from upstream execution (not static mock constant).
- `T1_F10_02_DynamicVersionReporting`: Health endpoint returns dynamic version (not static `"1.0.0"`).
- `T1_F10_03_AspectRatioValidation`: Aspect ratio validated against provider supported ratios.
- `T1_F10_04_DynamicProviderRouting`: Request routes dynamically to requested provider instead of fixed `"flow"`.
- `T1_F10_05_NoReadyAccountsResponse`: When no pool accounts are available, returns appropriate HTTP error (503/429) rather than synthetic fake image.

#### Feature 11: Handlers & DTO Modular Refactoring (R4)
- `T1_F11_01_HealthHandlerDTO`: GET `/health` serializes clean DTO with status, uptime, accounts.
- `T1_F11_02_GenerationHandlerDTO`: POST `/v1/images/generations` deserializes input DTO and outputs response DTO.
- `T1_F11_03_StandardErrorDTO`: Error responses adhere to `{error, message}` DTO schema.
- `T1_F11_04_BearerAuthMiddleware`: Middleware rejects missing or invalid Bearer tokens with 401.
- `T1_F11_05_RecovererMiddleware`: Middlewares handle panics gracefully without terminating server process.

### Tier 2: Boundary & Corner Cases (>=5 test cases per feature)

#### Boundary 1: Master Key Corner Cases
- `T2_B1_01_EmptyMasterKeyString`: Rejects empty string key and handles gracefully without panic.
- `T2_B1_02_ShortMasterKey`: Key shorter than 32 bytes derived via SHA-256 for cryptographic safety.
- `T2_B1_03_ExtremelyLongKey`: High-entropy key of 1024+ characters accepted and properly hashed.
- `T2_B1_04_BinaryNonUTF8Key`: Master key containing binary/non-UTF8 bytes handled safely.
- `T2_B1_05_ReadOnlyKeyFileDir`: Graceful error/warning if `.master.key` cannot be written to disk.

#### Boundary 2: Config Layering Corner Cases
- `T2_B2_01_MalformedConfigFile`: Malformed JSON in config file returns descriptive error on Load.
- `T2_B2_02_InvalidPortNumber`: Port <= 0 or > 65535 handled appropriately.
- `T2_B2_03_EmptyDataDir`: Empty data directory string defaults to `.` or standard path safely.
- `T2_B2_04_SpecialCharsInDBPath`: Database paths containing spaces and unicode characters work correctly.
- `T2_B2_05_NonExistentConfigFileFlag`: Explicit `--config` pointing to missing file returns clear error.

#### Boundary 3: Manifest Schema Corner Cases
- `T2_B3_01_EmptyManifestJSON`: Empty JSON object `{}` fails validation with missing required fields.
- `T2_B3_02_UnknownJSONFields`: Unknown extra JSON keys in manifest do not crash parser.
- `T2_B3_03_InvalidURLScheme`: Manifest with `ftp://` or `javascript:` URL rejected.
- `T2_B3_04_EmptyAllowedDomains`: Empty allowed domains list rejects non-base egress.
- `T2_B3_05_DuplicateProviderIDs`: Loading duplicate provider ID handles conflict gracefully (update or error).

#### Boundary 4: Manifest Loader Corner Cases
- `T2_B4_01_NonExistentManifestDir`: Missing directory returns error or uses embedded fallback.
- `T2_B4_02_EmptyDirectory`: Directory with no JSON files handles cleanly.
- `T2_B4_03_MixedValidAndInvalidFiles`: Directory with one valid and one corrupted JSON file reports error.
- `T2_B4_04_NonJSONFilesIgnored`: Non-JSON files (`.txt`, `.bak`) in manifest dir are ignored.
- `T2_B4_05_DeepSubdirectoryManifests`: Manifest scanner handles nested directory layout.

#### Boundary 5: Provider Registry Corner Cases
- `T2_B5_01_GetNonExistentProvider`: Querying unregistered provider ID returns `false` / not found.
- `T2_B5_02_RegisterNilProvider`: Registering nil provider pointer returns error without panic.
- `T2_B5_03_UpdateProviderStatus`: Transitioning provider between active and disabled state.
- `T2_B5_04_EmptyRegistryDefault`: DefaultProvider on empty registry returns `false`.
- `T2_B5_05_SpecialCharactersInID`: Provider IDs with dashes, underscores, and alphanumeric names.

#### Boundary 6: Entrypoint Seeding Corner Cases
- `T2_B6_01_DatabaseReopenIdempotency`: Restarting server with existing SQLite database preserves registered providers.
- `T2_B6_02_CLIHelpFlag`: Running binary with `--help` prints usage and exits cleanly with code 0.
- `T2_B6_03_UnknownCLIFlag`: Running binary with `--unknown-flag` returns non-zero error.
- `T2_B6_04_DuplicateStartOnSamePort`: Attempting to listen on already bound port returns descriptive error.
- `T2_B6_05_SIGINTShutdown`: Sending SIGINT/SIGTERM terminates HTTP server within graceful shutdown window.

#### Boundary 7: Account Pool Corner Cases
- `T2_B7_01_ZeroAccountsInPool`: Leasing from provider with 0 accounts returns pool exhausted error.
- `T2_B7_02_AllAccountsPaused`: All accounts currently `rate_limited` (`paused_until > now`) returns no ready accounts.
- `T2_B7_03_ExpiredPauseAutoRecovery`: Account with `paused_until < now` automatically transitions back to available.
- `T2_B7_04_ConcurrentLeaseContention`: 20 concurrent goroutines leasing from 2 accounts rotate without deadlocks.
- `T2_B7_05_LeaseReleaseIdempotency`: Releasing a lease multiple times is safe and idempotent.

#### Boundary 8: Credential Injection Corner Cases
- `T2_B8_01_ZeroCookiesInSecret`: Account with empty cookies slice constructs request without `Cookie` header.
- `T2_B8_02_ZeroTokensInSecret`: Account with empty tokens map constructs request without token headers.
- `T2_B8_03_SpecialCharsInCookieValue`: Cookies with quotes, semicolons, and URL-encoded characters preserved.
- `T2_B8_04_LargeCookieJar`: Account with 50+ cookies formats complete header within HTTP size limits.
- `T2_B8_05_CorruptedCiphertextSecret`: Account secret blob corrupted in SQLite returns decryption error gracefully.

#### Boundary 9: Reverse Proxy Corner Cases
- `T2_B9_01_UpstreamConnectionRefused`: Upstream server down / connection refused returns 502/504 error.
- `T2_B9_02_UpstreamTimeout`: Context timeout cancels upstream request cleanly.
- `T2_B9_03_UpstreamMalformedResponse`: Upstream returns invalid non-JSON body without crashing proxy.
- `T2_B9_04_Upstream429WithoutRetryAfter`: Upstream 429 without `Retry-After` defaults to exponential backoff.
- `T2_B9_05_UpstreamEmpty200Response`: Upstream 200 with empty body returns descriptive error.

#### Boundary 10: Handler De-Mock Corner Cases
- `T2_B10_01_EmptyPromptString`: Empty prompt returns HTTP 400 (`prompt is required`).
- `T2_B10_02_WhitespacePromptString`: Whitespace prompt (`"   \t\n  "`) returns HTTP 400.
- `T2_B10_03_VeryLargePrompt`: 64KB+ prompt accepted and forwarded properly.
- `T2_B10_04_UnsupportedAspectRatio`: Invalid aspect ratio string (`"99:99"`) handled according to spec.
- `T2_B10_05_NonExistentProviderRequest`: Request for non-existent provider ID returns 400/404 error.

#### Boundary 11: Modular Handler DTO Corner Cases
- `T2_B11_01_MalformedJSONBody`: Trailing comma, unclosed bracket in POST body returns HTTP 400.
- `T2_B11_02_WrongContentType`: POST with `text/plain` or missing content-type handled gracefully.
- `T2_B11_03_EmptyRequestBody`: POST with 0-byte body returns HTTP 400.
- `T2_B11_04_WrongHTTPMethod`: GET on `/v1/images/generations` returns 405 Method Not Allowed.
- `T2_B11_05_UnknownEndpoint`: GET on `/non-existent` returns 404 Not Found.

### Tier 4: Real-World Scenarios

- `T4_S1_FullLifecycleBootstrap`:
  Bootstrap gateway from config file -> Verify master key resolution -> Load manifests -> Register accounts -> Serve requests -> Query health -> Graceful shutdown.
- `T4_S2_MultiAccountConcurrentLoad`:
  10 concurrent clients submitting image generation requests against a pool of 3 accounts. Verifies fair rotation, absence of race conditions, and 100% completion.
- `T4_S3_CascadingFailoverAndRecovery`:
  Upstream returns 401 for Account 1 (marked signed out) -> Upstream returns 429 for Account 2 (marked rate limited) -> Account 3 succeeds. Pool exhaustion returns 503 when all accounts down. Once cooldown expires, Account 2 recovers.
- `T4_S4_HermeticGoogleFlowSimulation`:
  Complete end-to-end simulation of Google Flow upstream (`BatchGenerateImages` endpoint). Validates BOQ token headers, cookie parsing, upstream JSON response deserialization, and image URL delivery to client.
- `T4_S5_SubprocessCLIBinaryExecution`:
  Builds `cmd/server/main.go` into a binary, starts the subprocess with custom `--port` and `--data-dir`, tests HTTP endpoints over TCP socket, sends interrupt signal, and confirms clean termination.

## 4. Test Infrastructure Components

The test harness is implemented in `tests/e2e/harness.go`:
1. **`TestHarness`**: Manages temporary data directories, SQLite database, master key resolution, server instance, and HTTP test client.
2. **`MockUpstream`**: Standalone `httptest.Server` simulating upstream providers with configurable status codes, response bodies, header inspection, and request counters.
3. **Helper Assertions**: JSON body validation, status code checks, DTO parsers.
4. **Subprocess Runner**: Compiles and executes `cmd/server` binary for true out-of-process E2E testing.

## 5. Execution Instructions

Tests are executed with the standard Go test command:
```bash
go test -v ./tests/e2e/...
```

To run a specific tier:
```bash
go test -v ./tests/e2e/ -run TestTier1
go test -v ./tests/e2e/ -run TestTier2
go test -v ./tests/e2e/ -run TestTier3
go test -v ./tests/e2e/ -run TestTier4
```
